# PostgreSQL health snapshot

`postgres_health` appears only for PostgreSQL connections. It returns XID age (maximum across connectable databases), invalid or not-ready index count, unvalidated constraint count, maximum WAL bytes retained by a replication slot, and percentage of `max_connections` used by client backends. Each finding includes `observed_value`, `threshold`, `observed_at`, `severity`, and `state`. The full result is JSON text for older MCP clients and typed structured content for newer clients.

Default advisory warning/critical thresholds are 100M/180M transactions for XID age, 80%/95% connection utilization, 1/10 indexes or constraints, and 1/10 GiB slot retention. Missing values are `insufficient_data`; permission failures are `unavailable`. These are snapshots, not alerts or proof of a root cause. This count includes idle client sessions but not reserved-slot accounting; treat saturation as an approximation. A slot with no `restart_lsn` contributes no retention estimate. Investigate using authorized monitoring before acting; do not run maintenance or change schema based solely on this output.

The server never installs extensions or modifies database objects. Use a database role with read-only privileges. `execute_query` accepts only SELECT and WITH statements (including leading SQL comments and multiline queries); SHOW, DESCRIBE, and raw EXPLAIN are rejected because they cannot be wrapped reliably with a server-side row limit. Use the dedicated metadata and explain tools instead. A SELECT may still call side-effecting functions: PostgreSQL checkout transactions are set read-only (blocking `setval`), but a function with external effects or a privileged SECURITY DEFINER function is outside that boundary. MySQL read-only transactions do not prevent named locks or session variables; the executor rejects direct lock calls and variable assignment, and read-only MySQL checkouts use fresh physical connections so session state cannot leak through the pool. These controls are not a SQL sandbox; provision least-privilege database accounts and restrict dangerous routines. Query results have a hard 10,000-row application maximum even for supplied SQL with a larger LIMIT, and programmatic calls cannot request no limit. The serialized query, columns, and rows count toward the executor byte budget; server text/structured response caps still apply. PostgreSQL/MySQL stream rows and stop after the cap, but a single decoded cell is materialized before checking its size; this is not a hard memory limit. ClickHouse `execute_query` and `sample_data` remain supported, but the synchronous driver buffers results before application-side checks, and SELECT can invoke table functions with effects outside the database. A ClickHouse `max_result_bytes` setting did not prevent a 500KB single-cell response in testing; neither path has a hard memory guarantee. Use a restricted ClickHouse role and server-side resource limits for untrusted data.
